## Implementation

`/dashboard` (with `/staff` retained as a compatibility entry point) and every dashboard API and attachment request require a cryptographically verified Cloudflare Access JWT (issuer, audience, signature, expiry and maximum one-hour token age), followed by an active invite-only D1 staff record. Roles are enforced in the handlers. Database lookup on every request makes a dashboard account disable immediate on its next request. Role changes, exports, client deletion and audit-log reads require an administrator. Staff cannot disable their own administrator account.

The private UI has search, status/assignee/date/overdue filters, sorting, 25-row pagination, status totals, unread counts, follow-ups, linked client requests, proposal versions, and chronological messages, calls, private notes and status changes. Data comes from authenticated APIs. All responses are non-cacheable, noindex, have a restrictive CSP, and do not include analytics. Mutations require exact same-origin headers and JSON; database inputs are bound parameters and displayed content is escaped. Attachments are served as downloads only after authentication.

Migrations `0002_staff_dashboard.sql` and `0003_staff_roles.sql` add clients, enquiries, explicit staff invitations, activity history, proposal versions, webhook deduplication, attachment metadata and audit records. Enquiries use unique `WTA-date-random` references. The same normalized email links clients while each travel request has its own reference and history. Client details are not silently overwritten by subsequent public submissions.

`DASHBOARD_CAPTURE=true` enables durable capture for both contact-form and Journey Designer submissions. Journey Designer inserts its proposal and enquiry in one D1 transaction. Provider failures do not erase saved enquiries. Its outgoing customer email is archived, and proposal links are captured automatically. Customer replies through the proposal page are added to the timeline. Consultant edits require staff authentication once capture is enabled and preserve previous content snapshots while retaining the existing customer link. An old snapshot is an internal historical record: opening the reused customer URL shows its current content. Manual proposals can retain distinct URLs and versions. Sending a draft proposal URL from the dashboard marks that version sent.

Resend `email.received` events are signature-verified with Svix and the full message is retrieved server-side. Thread headers and explicit enquiry references are combined; conflicting or absent evidence goes to the unmatched queue. Sender email alone is never used to assign a reply. Incoming HTML is stored/displayed as escaped text when a plain-text body is unavailable. Provider IDs and webhook event IDs prevent duplicate messages. Non-content provider-ID tombstones prevent delayed retries from recreating deleted messages. Delivery events update archived outgoing messages; unrelated existing staff notification sends are not fabricated as customer messages. Client emails composed in the dashboard include only the explicit message, never internal notes. Sending uses Resend idempotency and has a 10-request/minute staff limit; ambiguous retries older than 23 hours require provider investigation.

Incoming attachment metadata is preserved. PDF, JPEG, PNG and plain text up to 10 MiB each (maximum 20 per message) are copied into private R2 before acknowledging the webhook. Other files are labelled blocked and not downloadable. No public R2 URLs or provider signed URLs are delivered to the browser. No staff upload or outgoing attachment composer is implemented; existing source did not support either. A malware-scanning service would be needed before permitting a wider attachment policy.

## Backups, restoration, retention and EU privacy decisions

The existing D1 database's EU jurisdiction was verified. This does not establish EU-only processing for email, identity or application execution. Cloudflare (Pages/Access/D1/R2) and Resend receive relevant customer/staff data. Review their DPAs, subprocessor lists and international-transfer arrangements. The existing public Journey Designer also has OpenAI and supplier/research services; this dashboard does not add those services to internal notes or communications. Update the public privacy notice before enabling new capture and establish lawful basis, access controls and a breach response procedure. This implementation is not a legal compliance certification.

Before launch, the owner must choose retention periods for open and closed enquiries, unmatched messages, attachments, provider copies, audit logs and backups, and designate a responsible reviewer. No automatic destructive retention job is enabled without that decision. Staff can filter closed enquiries by date; admins can export one enquiry or all linked client records (including timelines, proposal versions and attachment metadata) and explicitly delete a client and **all** their linked enquiries, archived messages, original linked proposals and R2 objects. Audit actor identifiers matching a deleted client email are anonymised. This does not delete existing provider email copies or backup copies: those require provider retention/deletion processes. Unmatched emails require separate manual review and deletion procedures; currently they can be assigned but not deleted from the UI. Do not claim a complete historical communication archive: no history was imported, unrelated mailbox messages remain outside the dashboard, and integration activation is still pending.

Cloudflare D1 Time Travel provides a rolling recovery window; verify the actual plan's window before relying on it. Before any production migration, export D1 to an encrypted, access-controlled backup destination and record a restore bookmark. Establish scheduled encrypted database exports and private attachment backups with owner-selected retention. Source migrations are reproducible but are not a backup of data. Example commands (execute only for the authorised environment):

```sh
npx wrangler d1 export DATABASE_NAME --remote --output /secure/location/backup.sql
npx wrangler d1 time-travel info DATABASE_NAME
npx wrangler d1 time-travel restore DATABASE_NAME --bookmark APPROVED_BOOKMARK
```

Restoration procedure: disable capture/sending and protect the environment; restore to a separate isolated database where possible; compare row counts, foreign keys, enquiries and proposal snapshots; restore R2 objects from the independent attachment backup; reapply required migrations; verify disabled staff still cannot access data; reconcile webhook deduplication and delivery status before replaying events; bind the verified database; test privately, then reopen after owner approval. Time Travel does not restore R2. Backups may contain deleted client data; keep them isolated, expire them under the agreed policy, and reapply deletion records after recovery.
